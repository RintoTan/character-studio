## 4. 阶段 3：1.x 与 2.x 的领域化（1.0.0 – 2.0.1）

### 4.1　1.0.0（Sprint 9.0）—— 本地优先工作台成为可发布基线

这一版**没有加新功能面**，做的是「把已有的 1.0 做到敢发布」：

- **测试从 0 到 51 个**（vitest + happy-dom + fake-indexeddb），接入 CI 在构建前执行。
- 发布自动化：push `main` → typecheck → test → build → 部署 GitHub Pages；构建注入 commit 与时间戳。

### 4.2　1.1.0 / 1.2.0 / 2.0.0 —— 三个领域

| 版本 | 领域 | 关键设计约定 |
| --- | --- | --- |
| 1.1.0（9.1） | **角色关系网** | 关系是**独立集合**而非写进角色记录（一条边属于两个角色）；8 种类型；点击节点进入该角色展示页 |
| 1.2.0（9.2） | **世界观时间线** | 支持**架空历法**：事件同时带可排序的真实日期与可选的纪年标签，**排序永不依赖标签** |
| 2.0.0（10.0） | **世界观管理** | 地点 / 势力 / 种族 / 物品 / 概念，支持层级（国家下辖城市）、标签与角色关联 |

三个领域共同的设计约定：

- **删除的语义是「断开」而非「连带删除」**：删角色会从事件与世界观条目中移除该角色的关联，**但事件与条目本身保留**；删世界观父级时子级变为顶层而不是一起消失。
- **读取即修复**：损坏的存储值、缺关键字段、未知类型、重复 id、悬空引用、成环层级都在读取时被安全处理。
- **空壳开关不再存在**：`experimentalRelationshipGraph` / `experimentalTimeline` 此前「已声明、界面上展示、却从未生效」，现在真正控制入口；`worldManager` 为新增同类开关。

### 4.3　2.0.1（10.1）—— About 显示过期版本号

根因：Version / Sprint 读的是 `localStorage` 里的 `developerSettings.project`，而它只在首次运行时取一次默认值，之后永久驻留。
修法：版本一律取自编译进包的常量；开发者中心这五个字段改为**只读**（允许编辑它们正是该 bug 的成因）。用户已存的旧值不删除，只是不再被任何界面读取。

## 6. 阶段 5：数据可靠性 → 架构收敛 → 界面返工（2.12.0 – 2.27.0）

### 6.1　阶段 A：数据与状态可靠性（2.12.0，Sprint 22.1）

| 项 | 内容 |
| --- | --- |
| 调查更正 | 规划初稿写「引用清理发生在下次挂载而不是删除时」，读码后事实是：**单删路径一直会清理**，**批量删除不会**；三个域页面各自在挂载时清理自己的域，存储层的 load 不做自愈。残留风险是**在这个窗口内导出的备份会带解析不到的 id，而导入校验会丢弃它们**（恢复时静默少东西） |

## 7. 累计的测量与方法教训（可复用的纪律）

从 2.5.0 起，几乎每一版都在「验证动作本身产生了假信息」上踩过一次。归纳成可直接执行的四条：

1. **先验证观测点有没有区分度**，再拿它去测被测行为。已踩过：观测点选错（把恒存在的容器当状态指示器）、对照起点不同（profile 停在别的视图）、空 DOM 让所有断言为真。
2. **断言的对象要和动作的对象是同一个。** 2.27.0 的滚轮验证第一次把点打在 `y=560`，而画布只到 `y=540`，断言却校验「预记录的中心点」→ `inside: true` 通过、结论却是错的。**并且**：合成 `WheelEvent` 不执行默认行为，只有真实 CDP `Input.dispatchMouseEvent` 能回答「页面会不会滚」。
3. **改动与验证必须分成两轮。** 同一条回复里的工具调用会并行执行，编辑与读取同批会读到旧内容（曾把「还没落盘」误判成「没生效」，三次）。做结构化改写前先备份。
4. **报告前先把可疑读数拆成原始几何。** 1440 下的 `rows: 2` 与 `overflowInside` 是度量假象：5 个控件的 `top` 是 354/354/354/**351**/354（主按钮高 3px 被「按 top 分组」算成两行），而绝对定位的隐藏 file input 与浮层污染了 `scrollWidth`。

另外三条工程性纪律：

5. **脏工作树会改变构建产物**（提交号带 `-dirty` → 内容哈希变化）→ 必须**先提交、再重建、再跑 `verify:deploy`**。
6. **图标按钮没有文字** → 用 `aria-label` 查找，并加「空结果即返回错误」的前置断言，否则探针会拿到空结果并「看起来没问题」。
7. **`git commit -m` 里的反引号会被 zsh 当命令替换吞掉** → 用 `-F file`。

## 12. Sprint 38.1：数据安全决策落实（2026-10-15）

Sprint 38 把问题查清了，Sprint 38.1 落实所有者给出的六项决策（DEC-38-01…06）。仍不新增功能、不改 UI。

### 12.1 DEC-38-01：快照写失败时必须阻止清空 —— 一次正式的安全决策变更

**原有相反规则**：`src/storage/backup.ts` 里写着「A full quota must never block the operation the user actually asked for」，即配额满时静默返回 `null`、继续执行。该行为从快照机制第一天起就在，并且被注释明确记录为有意为之。

**为什么改**：`createSnapshot` 用同一个 `null` 同时表示「没有需要保护的数据」和「快照写失败」。调用方因此无法区分，于是「写失败」被当成「没什么要保护的」放行 —— 而这类操作的确认文案恰恰承诺过「会自动保留一份可恢复的备份」。承诺与实际相反时，静默的那一侧会赢。DEC-38-01 把这条改成严格保护。

**实现**：
- `src/storage/backup.ts` 新增 `attemptSnapshot()`，返回 `empty | created | failed`（失败带原因），两个状态不再混为一谈；`createSnapshot()` 保留原契约（`snapshot | null`）供**导入**路径继续使用，其注释已改写以说明差异。
- `src/storage/localDataReset.ts` 的顺序固定为：读旧快照 → 尝试写快照 → **失败即返回，不做任何删除** → 成功才 `localStorage.clear()` → 回写快照。
- `src/App.tsx` 与 `src/pages/Dashboard.tsx`：失败时给用户明确提示（App 在对话框内显示 `form-error`，Dashboard 用既有 toast），保持数据不变，请用户清理存储空间或自行导出后再试。**没有**「忽略备份失败、仍然清空」按钮。
- **入口检查**：全库 `localStorage.clear()` 只允许出现在 `src/storage/localDataReset.ts`（由测试守卫），两条清空入口都调用该 helper；`createSnapshot` 的其余调用点只有导入路径（`Dashboard.tsx` 导入前备份），**该路径仍为非阻断**，已登记为 R-33，不在本次扩大范围。

**测试**：`test/localDataReset.test.ts`（17 例）。注入 `localStorage.setItem` 只对备份键抛错（`QuotaExceededError` 与其它错误名分别断言），确认删除没有发生、无关键未被清理、空列表仍可清空、失败后可重试。变异检验：移除阻断 → **4 条**失败。

**真实浏览器**：`npm run verify:browser` 的「快照写入失败时不清空数据并要求用户处理」→ 角色仍为 2 个、对话框显示「自动备份失败」；随后写入恢复 → 清空成功且快照保留 2 个角色。

### 12.2 DEC-38-02 / TASK-38.1-05：不再把角色快照说成完整备份

当前快照只含角色记录。两条清空入口的确认文案改为：备份里**只有角色文字资料**，而头像素材、角色关系网、世界观时间线、世界观条目与全部设置**不在其中**、清空后无法用它找回。文本避免「完整备份」「所有数据都可恢复」这类说法，也没有引入存储术语。扩大快照覆盖范围属改存储协议，登记为 R-27。

## 13. Sprint 38.2：删除操作的数据恢复（2026-10-16）

本轮只处理 KI-17 / R-32。起点 `d9098c7`，未推送、未部署、未改版本号。

### 13.1 为什么不能只「让撤销也回写关联」

最直接的修法是让 `Dashboard.restoreDeletedCharacter()` 顺手把关联写回去。做不了，因为它**不知道该写回什么**：`pruneCharacterReferences()` 已经把引用从三个存储域里删掉了，删除之后没有任何地方留有「原来是什么样」的记录。撤销拿到的只有那个 `Character` 对象。

所以需要的是**删除前的一份记录**，而不是恢复时更多的逻辑。这也解释了为什么原登记的方案（第二份快照）是对的方向。

### 13.2 数据结构：记录「删除会改什么」，而不是「整个工作域」

有两条路：把三个工作域整体存一份，或只存**这次删除会动到的部分**。选了后者：

| 域 | 删除会做什么 | 记录什么 |
| --- | --- | --- |
| 角色 | 移除该角色 | 被删角色对象 |
| 关系网 | 删掉以它为端点的边 | 这些边本身（`id` / `fromId` / `toId` / `kind`） |
| 时间线 / 世界观 | 只从参与列表里去掉它，条目仍在 | 受影响条目的 `id` + **原有参与列表** |

记录因此与数据量成正比的是「这次删除影响到的部分」，而不是整个工作域；也不需要对三个域做序列化协议（`workspaceBackup.ts` 已有的能力留在导入导出路径上，未重复实现）。

### 13.3 恢复为什么用「合并」而不是「还原」

反过来等价于「把存储恢复成删除前的样子」，那会**覆盖删除之后的一切**。这在一部作品里是最糟的：删除之后新建的角色会被抹掉。所以恢复是合并：

- 角色：只补不在列表里的 id；
- 关系边：只补 id 不存在、**且两端角色都在**的边；
- 时间线 / 世界观：只往参与列表里补缺失的 id；**记录里有、但条目已被单独删除的，不重建** —— 那是用户之后自己的决定。

同名不同 ID 的角色因此不可能被错认：全过程按 id 匹配，名字不参与判断（KI-14 的教训在这里第二次生效）。

### 13.4 多个键的写入不是事务

三个工作域的 `saveX()` **内部把写入异常吞掉了**（当初的设计是「配额满不得让页面崩溃」），所以调用方无法用 try/catch 判断成功。这是本轮最重要的一个约束：

- **不假设原子性**：每一步写入后**读回校验**，只有读回结果里确实含有要恢复的内容才算成功；
- **失败保留记录**：因为每步只补缺失项，所以恢复是**幂等**的 —— 写入失败时保留记录，再按一次撤销就能接着做完，而不会重复添加；
- **不把部分当完整**：只要有一步没落地，结果就是 `partial` 并说明原因；`restored` 只在全部落地时返回。

角色写入是唯一有异常的路径，所以它在最前面：**角色先落地并校验，再动任何引用** —— 先写引用会得到指向不存在角色的悬空引用，正是这个记录要防止的事。

### 13.5 撤销入口为什么要由 App 持有

编辑器里的删除发生在另一个页面，删完就 `onCancel()` 回到主页，编辑器里没有可以放撤销的位置（此前也就没有）。做法是把请求交给主页而不是在两个页面各写一份：`App` 持有 `deleteUndo { characterIds, message }`，主页把它变成一个 10 秒的撤销卡片（`showUndoToast`，逻辑未改，只是触发来源合并了）。三个入口因此是**一个机制**，不是三套。

`CharacterForm` 的删除现在读取 `onDelete` 的返回值：被拒绝时**留在编辑页**并提示原因 —— 否则界面会离开一个其实还在的角色。

### 13.6 测试：这次先问「断言有没有区分度」

新增两个文件：数据规则 13 例（`test/deleteRecovery.test.ts`）、入口接线 3 例（`test/deleteEntryPoints.test.ts`，**渲染真实 `App`** 走主页单删 / 批删 / 拒绝删除，因为 KI-17 的 bug 本来就在调用点上而不在算法里）。

| 变异 | 失败用例 |
| --- | --- |

### 13.7 一处自己的预期错在测试里（不是产品里）
